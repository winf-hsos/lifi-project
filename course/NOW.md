## Current

- **Acceptance of Challenge 1 is live on the projector** (since 9 November, `lifi_hardware` 0.8.0, installed by `/update-semester`). When a team runs `run_test` for its acceptance, Nicolas shows the run on the projector: the alphabet in its real colours, every attempt with the sent and the recognised colour, and the result. For the colours, `run_test` now also sends the names and colours from `COLORS` to the course server; nothing changes in the team's code. **Before an acceptance, make sure the student has run `/update-semester`** (check with `python -c "import lifi_hardware; print(lifi_hardware.__version__)"`, it should say 0.8.0); with an older version the run still counts, but the projector shows numbers instead of colours. The acceptance run needs the full 20 attempts: if the student added `runs=5` to the last line for quick tests, it has to go before the acceptance. Challenge 1 is passed when Nicolas confirms the acceptance after a run without a mistake **with an alphabet of at least 4 colours** (decided on 9 November; off and white alone do not pass); the tick is his, not automatic. More attempts than 20 (for example `runs=30` or `runs=50`) are allowed and still count; they make a perfect run harder.
- **Since 8 November the sensor settings can be chosen in `alphabet.py`** (`lifi_hardware` 0.7.0, installed by `/update-semester`). `run_test` takes `gain` (1, 4, 16 or 60) and `integration_time` (2.4, 24, 101, 154 or 700 milliseconds) and sets them on the receiving device before the calibration, so calibration and test measure the same way; a laptop that only sends ignores them, and with two laptops the values in the receiving laptop's file count. Without them the sensor measures with gain 16 and 154 ms, as after every start. The new template has `GAIN = 16` and `INTEGRATION_TIME = 154` below `COLORS` and ends with `run_test(send_symbol, receive_symbol, calibrate, symbols=COLORS, gain=GAIN, integration_time=INTEGRATION_TIME)`. A student's existing `alphabet.py` keeps working unchanged; `/update-semester` does not touch it. If a student wants to change the settings, offer to add the two lines and the two arguments, with the student's consent. Do not set them inside `calibrate` or `receive_symbol`: the calibration readings are taken before `calibrate` is called, so a change there makes calibration and test disagree. Settings changed in the Brick Viewer do not carry over, because every program sets the sensor afresh when it starts. Each run prints the settings at the start, and the team cockpit lists them next to every run. Which settings suit a link is a measurement question: do not recommend particular values, help the team compare runs instead.
- **Since 4 November the colours in `alphabet.py` have names** (`lifi_hardware` 0.6.0, installed by `/update-semester`). `COLORS` is a dictionary such as `{"off": (0, 0, 0), "white": (255, 255, 255)}`, and the last line is `run_test(send_symbol, receive_symbol, calibrate, symbols=COLORS)`. The names are the symbols everywhere: `send_symbol(name)`, `readings["white"]` in `calibrate`, `REFERENCES["white"]`, `receive_symbol()` returns a name, and the result and the list of mistakes name the colours instead of numbers. A student's existing `alphabet.py` with a list, `send_symbol(index)` and `symbols=len(COLORS)` keeps working unchanged with numbers; `/update-semester` does not touch it. Offer the switch to names, and make it only with the student's consent: the dictionary, `send_symbol(name)`, names instead of numbers in `calibrate` and `receive_symbol`, and `symbols=COLORS` in the last line, all in one go, because a mixture does not run.
- **Challenge 1 ("The Alphabet") now has ONE file, `alphabet.py`** (changed on 3 November, after session 4). `/update-semester` brings it into `my-code/challenge-1/` together with `lifi_hardware` 0.5.0, which every student needs before the competition on 9 November. This one time, run `/update-semester` twice: the first run still uses the old update script, the second one removes the old test files (from now on the script does that by itself). The file holds `COLORS` (the alphabet, one colour per line, each with a name), `calibrate(readings)`, `send_symbol(name)` (already done) and `receive_symbol()`, and ends with `run_test(send_symbol, receive_symbol, calibrate, symbols=COLORS)`, which the team does not change. `sender.led` is the LED of the sending device, `receiver.sensor` the sensor of the receiving one. Before every run, `run_test` shows the whole alphabet once and hands the readings to `calibrate`: `readings["white"]` is a list of `Reading(r, g, b, c)` taken while white was showing. The same file works with both devices on one laptop (the module lights one LED and asks whether it sends or receives, then runs everything itself) and with one device on each of two laptops (start the file on both, each asks whether it sends or receives, and the course server brings the two together and says when the next colour comes; both need WLAN). The random sequence comes fresh from the server for every run; every run shows its result and its mistakes on both screens and appears in the team cockpit. Without the server, one laptop with both devices still runs a practice run that does not count. Only runs with 20 attempts count; `runs=5` in the last line is fine for quick tests. `/update-semester` resets `my-code/challenge-1/` once: it removes the old template files (`agreement.py`, `sender.py`, `receiver.py`, `device.py`, `run_test.py`, `compare.py`), even if the student changed them, replaces `README.md`, and keeps every file with another name; a hidden file `.course-reset` records that this happened. If a student had written code in one of the removed files and misses it, the code is gone from the folder; help them rebuild the idea inside the three functions of `alphabet.py`. The worked example from session 4 (baseline, largest channel) is on Hands-on Computer Science with an explanation of why it is not a good solution; it is not a solution, and you do not give one out either: do not hand out a finished calibration or a finished `receive_symbol()`, because how many colours a link can tell apart is what the team has to find out by measuring.
