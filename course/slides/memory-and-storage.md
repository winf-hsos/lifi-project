# Lecture notes: "where the bytes live" (Memory and Storage)

These notes explain the deck on the concept Memory and Storage, for reading afterwards. They follow the order of the slides (the numbers are frames, and build-up steps count separately) and can be read as a text of their own. For Challenge 4 they are required reading: there, for the first time, a whole file is read, sent and written again on the other side.

The concept was created on 16.09.2026 from two pages that overlapped anyway: `memory` ended with a section on files, `files` with one on memory. The logic level, that is the flip-flop built from gates, stays in the concept Logic and Arithmetic and is only borrowed from there.

## Part 1: a file is a sequence of bytes (Frames 3 to 14)

**Where do 196 662 bytes live? (Frame 4).** The photo of the parrot is 196 662 bytes in size. Where are they right now? Two answers, and both are right: in main memory, as long as the image is open, and on the disk, since you saved it. In the photo both places lie open side by side, the mirror-like platter of a hard disk and a memory module. This deck answers both, and in between the question of what is actually in such a file.

**The same file, two programs (Frame 5).** Open an image file in a text editor and you see nonsense: the editor reads every byte as a character and shows a dot wherever the byte does not make a printable character. The hex editor shows the same bytes as two-digit hex numbers, without any interpretation. The file is fine in both cases; the only thing that changed is the reading rule. That is the same thought as with the carrier: data on its own means nothing, and somebody has to add the rule for how to read it.

**78 bytes, all of them (Frames 6 to 9).** The smallest useful example is a bitmap of four by two pixels, 78 bytes long. Everything a large file has, this one has too, only in an amount you can read out loud. It splits into three parts: the first 14 bytes are the file header with the signature "BM", the size of the file and the position where the pixels begin. The next 40 are the info header with width, height and colour depth. The last 24 are the image data. Exactly these bytes are also in the demonstrator Inside a File.

**The header says how to read the rest (Frame 10).** Four fields are enough to show it. At byte 2 the file size stands as `4e 00 00 00`, so 78; that the lowest byte comes first is another agreement of this format. At byte 10 it says where the pixels begin: `36 00 00 00`, so at byte 54. At byte 18 is the width, at byte 28 the colour depth `18 00`, so 24 bits and therefore three bytes per pixel. With that the program knows, without having seen a single pixel, that from byte 54 exactly 4 times 2 times 3 equals 24 bytes follow, and that is exactly how long the rest of the file is. The header fields are to the program what the type field and the length field in the frame of Challenge 4 are to your receiver: the announcement of what is coming and how to read it.

**Two decisions from 1990 (Frame 11).** The second stored pixel reads `00 ff ff`. Anyone who now says "cyan", because red is off and green and blue are on, is wrong: this format stores the three components in the order blue, green, red, so the pixel is yellow. And the first stored row is not the top one but the bottom one; bitmaps stand upside down in the file. The top row of the image only begins at byte 66, with a pure red. The point is not the colour but the arbitrariness: both could have been decided differently, and they hold anyway, because every program sticks to them. That is a file format: not a law of nature, but a written agreement. You wrote exactly such an agreement yourselves in Challenge 3.

**How does a program recognise the type? (Frame 12).** Three answers, all three of them labels next to or in front of the data. The file extension is in the name, not in the file; renaming it does not change a single byte, and that is why you can also lie with it. The magic bytes are in the file itself, here "BM", with PNG eight fixed bytes, with PDF `%PDF`; they are not mandatory, a text file begins with its first letter, and that is why no program can reliably guess the type. The type field in your frame is the third answer and the cleanest one, because the class decides which number stands for which type.

**The demonstrator (Frame 13).** Inside a File. Change a byte in the pixel data: the image is displayed, one dot is wrong, and you have to search for it. Change a byte in the header, the width for instance: the viewer shows stripes or refuses the file altogether. A broken byte in the data is a small injury, one in the header a large one, and that is why in the final the hash decides everything.

**What a file is (Frame 14).** A sequence of bytes plus an agreement about how to read it. Nothing more, and that holds for every file on your computer.

## Part 2: where the bytes live (Frames 15 to 26)

**A bit that remembers (Frames 16 to 18).** You know the gates from the toolbox; here they get a new purpose. Two NOR gates wired crosswise: a short pulse on `set` makes the output 1, and when `set` is off again it stays 1, because the two gates keep feeding each other. That is one bit of memory, built from the same switches that also add and compare. Eight of them side by side hold a byte, and that is a register, the fastest memory in the computer. The gate does not know whether its bit belongs to a number, a letter or a pixel.

**Millions of them, each with a number (Frame 19).** Main memory is a very long row of such cells, and none of them knows what it holds. The processor puts an address on the address lines, and the row answers on the data lines; for writing it is the other way round. That is why a program never says "the number over there", but "the byte at address 4711". The number is the only handle the machine has. Names for memory locations are only invented by the programming language, and it translates them into addresses.

**Power gone (Frames 20 and 21).** The flip-flop keeps its one only as long as the two gates can feed each other. Once the power is gone, the loop collapses, immediately. Nobody deletes anything, and the operating system does not even get the chance. That is why a text that was not saved is lost after a crash. The price is paid on purpose: main memory answers in nanoseconds because nothing has to move.

**What a bit is made of here (Frame 22).** Five ways of building one, side by side. In main memory a loop that has to be fed. On the hard disk a tiny spot that is magnetised in one direction or the other; a head floats just above it, flips it to write and senses it to read. In flash memory a charge trapped in a transistor that is insulated on all sides, where it stays for years; reading means checking whether it is there. On the CD a pressed pit or a flat spot. On magnetic tape the same as on the disk, only in one long line instead of on a circle, which makes searching slow and keeping cheap; archives still store data this way today, for decades. Only the first one needs power. And none of the five knows whether its bit belongs to a parrot.

**A CD reads bits with light (Frame 23).** On the surface runs one single spiral from the inside outwards, and along it lie flat spots and pressed pits. A laser shines from below. On a flat spot the light comes back into the sensor, in a pit it scatters away, and almost nothing arrives. There is the bit, and there is your link: a lamp, a sensor, and a reflection that arrives or does not. Your device does exactly the same thing, except that your sender is an LED you control and the CD's sender is a pit that was pressed years ago. And the CD shares one more thing with your project: scratched, it usually still plays, because massive redundancy is built in. Whoever designed the format assumed that discs get scratched and paid for it in advance, just like with the torn QR sticker in the concept Errors and Redundancy.

**The medium outlives its reader (Frame 24).** A floppy disk from 1995 still holds its magnetisation today; what is missing is the drive, and often also the program that knows its format. The physical state on its own is not information yet: the agreement for interpreting it has to survive just as much as the material. And with that we are back at Part 1.

**What saving means (Frame 25).** When you click Save, the bytes are copied from main memory into a store that holds without power. Copied, not moved: afterwards they are in both places, and they are the same bytes. Main memory also does not write itself away at intervals by itself; some programs make their own backup copies, but that is a decision of the program.

**Four places, one sequence (Frame 26).** Register, main memory, disk and flash, CD and tape. From top to bottom it gets slower and more durable, and that is no coincidence: the fastest place is the one where nothing has to move, and exactly that needs power all the time.

## Part 3: on your link (Frames 27 to 30)

**The whole way (Frame 28).** From the disk into main memory, from there byte by byte into symbols, the symbols become light, on the other side symbols again, bytes again, main memory again, disk again. At no point is it a picture; it is always the same sequence of bytes, only in different places and in different materials. At the same time this is the map of the module seen from below: storing, representing, transferring and processing, all in one single operation.

**What this means for Challenge 4 (Frame 29).** Read the file as binary, not as text, or the character encoding will change your bytes. Send the header along, or the receiver cannot do anything with it. And check the hash at the end, not the appearance: that an image is displayed proves nothing. Plus the sentence that follows from the demonstrator: a byte you change in the header costs you the whole file.

**Closing (Frame 30).** A magnetised spot, and that is your photo. That is all it is, and that is exactly why it can be sent through a lamp.
